# Code Standards

These rules take precedence over any conflicting guidance elsewhere (including the Ultracite defaults in `AGENTS.md`). They apply to `.ts` / `.tsx` files unless stated otherwise. Vendored code (`src/components/ui/`, generated by shadcn, and `.claude/skills/`) is exempt.

Ultracite enforces `func-style: expression`, so every function is an arrow function assigned to a `const`. The examples below follow that.

## No comments

Don't write comments. Code should explain itself through naming and structure. The only exception is something non-obvious that code can't express, such as a complex regex or a workaround for a browser bug.

```ts
// Bad
// check if the url is a github repo
const re = /^https:\/\/github\.com\/[\w.-]+\/[\w.-]+\/?$/;

// Good — comment justified, the regex intent isn't obvious from reading it
// Matches "https://github.com/<owner>/<repo>", optional trailing slash
const GITHUB_REPO_URL = /^https:\/\/github\.com\/[\w.-]+\/[\w.-]+\/?$/;
```

## File size limit

No `.ts` / `.tsx` file over 100 lines. If a file grows past that, split responsibilities into separate files (extract components, hooks, helpers, types, content data).

## Function size limit

Functions must be at most 30 lines. If the behavior needs more, split it into smaller, well-named functions.

```ts
// Bad — one 40-line function that sorts, filters and formats the experience timeline

// Good
const sortByStartDate = (entries: Experience[]): Experience[] => {
  /* ... */
};
const filterVisibleEntries = (entries: Experience[]): Experience[] => {
  /* ... */
};
const formatPeriod = (entry: Experience): string => {
  /* ... */
};
```

## Max 3 levels of nested if/else — prefer guard clauses

Don't nest conditionals more than 3 levels deep. Use early returns (guard clauses) instead of accumulating nested logic.

```ts
// Bad
const getProjectBadge = (project: Project) => {
  if (project) {
    if (project.isPublished) {
      if (project.liveUrl) {
        return "Live";
      }
    }
  }
  return null;
};

// Good
const getProjectBadge = (project: Project) => {
  if (!project) {
    return null;
  }
  if (!project.isPublished) {
    return null;
  }
  if (!project.liveUrl) {
    return null;
  }
  return "Live";
};
```

## Max 3 parameters — use param objects

Functions take at most 3 parameters. If more are needed, group them into a param object.

```ts
// Bad
const createProject = (
  title: string,
  summary: string,
  stack: string[],
  repoUrl: string,
  liveUrl: string
) => {};

// Good
type CreateProjectParams = {
  title: string;
  summary: string;
  stack: string[];
  repoUrl: string;
  liveUrl: string;
};

const createProject = ({
  title,
  summary,
  stack,
  repoUrl,
  liveUrl,
}: CreateProjectParams) => {};
```

## No blank lines inside functions

Don't leave blank lines inside a function body. Blank lines between top-level declarations in a file are fine.

```ts
// Bad
const yearsOfExperience = (entries: Experience[]) => {
  const firstStart = Math.min(
    ...entries.map((entry) => entry.start.getFullYear())
  );

  return CURRENT_YEAR - firstStart;
};

// Good
const yearsOfExperience = (entries: Experience[]) => {
  const firstStart = Math.min(
    ...entries.map((entry) => entry.start.getFullYear())
  );
  return CURRENT_YEAR - firstStart;
};
```

## Extract magic numbers/strings into constants

Replace magic numbers and strings with named constants that make the concept explicit.

```ts
// Bad
const featured = projects.slice(0, 3);

// Good
const FEATURED_PROJECTS_COUNT = 3;
const featured = projects.slice(0, FEATURED_PROJECTS_COUNT);
```

## Declare variables close to where they're used

Don't declare a variable far above its first use. Declare it right before the block that needs it.

```ts
// Bad
const period = formatPeriod(entry);
const company = getCompany(entry.companyId);
// ...many lines later
renderPeriod(period);

// Good
const company = getCompany(entry.companyId);
// ...
const period = formatPeriod(entry);
renderPeriod(period);
```

## Never hardcode sensitive data

API tokens, secrets and credentials never go in code. This is a static site on GitHub Pages: everything in `src/` and every `import.meta.env.VITE_*` value ends up in the public bundle, so secrets don't belong in the client at all. Only public configuration may be read from `import.meta.env.VITE_*`, with a matching entry in `.env.example` (no real value).

```ts
// Bad — a token baked into the bundle is visible to every visitor
const githubToken = "ghp_abc123";

// Good — public, non-secret config only
const githubUsername = import.meta.env.VITE_GITHUB_USERNAME;
```

## Type safety and explicitness

- Use explicit types for function parameters and return values when they enhance clarity
- Prefer `unknown` over `any` when the type is genuinely unknown
- Use const assertions (`as const`) for immutable values and literal types
- Leverage type narrowing instead of type assertions
- No `enum` or `namespace` (`erasableSyntaxOnly`); use union types and plain objects
- Type-only imports use `import type` (`verbatimModuleSyntax`)

## Modern JavaScript/TypeScript

- Arrow functions everywhere, including components and helpers
- Prefer `for...of` loops over `.forEach()` and indexed `for` loops
- Use optional chaining (`?.`) and nullish coalescing (`??`) for safer property access
- Prefer template literals over string concatenation
- Use destructuring for object and array assignments
- Use `const` by default, `let` only when reassignment is needed, never `var`
- Object literal keys in alphabetical order (`sort-keys`)

## Async and promises

- Always `await` promises in async functions and use the return value
- Use `async/await` instead of promise chains
- Handle errors in async code with `try/catch`
- Don't use async functions as Promise executors

## Error handling and debugging

- Remove `console.log`, `debugger` and `alert` from committed code
- Throw `Error` objects with descriptive messages, not strings or other values
- Use `try/catch` meaningfully; don't catch errors only to rethrow them

## Security

- Add `rel="noreferrer"` when using `target="_blank"` on links
- Avoid `dangerouslySetInnerHTML`; render content as JSX
- Don't use `eval()` or assign directly to `document.cookie`
- Validate and sanitize anything read from URLs, forms or external APIs

## Performance

- Avoid spread syntax in accumulators within loops
- Use top-level regex literals instead of creating them in loops
- Prefer specific imports over namespace imports (`import { GithubLogo } from "@phosphor-icons/react"`)
- Avoid barrel files (index files that re-export everything)
- Import images from `src/assets/` so Vite hashes them, and give every `<img>` explicit `width`, `height` and `loading="lazy"` when below the fold
